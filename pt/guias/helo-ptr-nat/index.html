HELO, PTR e NAT: os novos requisitos da Spamhaus

Desde novembro de 2026 a Spamhaus vigia como se apresenta cada servidor de email. O que exige, como verificar os seus IPs passo a passo e porque o NAT pode estragar tudo.

O que mudou

A 21 de outubro de 2026 a Spamhaus anunciou que, gradualmente a partir de novembro, cada IP que envia email tem de ter um HELO válido, um DNS inverso (PTR) e um registo A coincidente. Segundo a Spamhaus, falhas nestes pontos podem fazer com que o IP entre nas suas listas CSS ou XBL, que milhares de fornecedores consultam antes de aceitar um email.

Não é uma ideia nova: o Gmail já exige a todos os remetentes DNS direto e inverso válidos. A novidade é que a Spamhaus o vigia ativamente, e um servidor legítimo pode acabar na mesma lista que uma máquina infetada só por se apresentar mal.

As peças, sem tecnicismos

Pense num estafeta que chega à receção de um edifício:

  • O IP é a matrícula da carrinha.
  • O PTR é o que diz o registo de matrículas: a quem pertence essa carrinha (o IP diz como se chama).
  • O registo A confirma que essa empresa tem mesmo essa matrícula (o nome diz que IP tem).
  • O HELO (ou EHLO) é o que o estafeta diz ao chegar: «venho da empresa tal».

Se as três coisas coincidirem, a encomenda passa. Se não, a receção desconfia, e no email isso significa rejeição ou pasta de spam. Quando o IP e o seu PTR se confirmam mutuamente fala-se de FCrDNS (DNS inverso confirmado).

O que exige exatamente a Spamhaus

  • O IP tem um PTR.
  • Esse nome resolve para o mesmo IP (FCrDNS).
  • O HELO é um nome completo (por exemplo, mta1.envios.asuaempresa.com) que resolve para o IP que envia.
  • Recomendado: que o HELO coincida com o PTR.

E proíbe expressamente:

  • Valores de preenchimento como localhost ou localhost.localdomain.
  • Um HELO com forma de IP.
  • O nome genérico do fornecedor de alojamento (do tipo ip-203-0-113-25.fornecedor.net).
  • Um HELO que aponte para máquinas que não enviam email ou que se faça passar pelo Gmail, Hotmail ou outros fornecedores.

Como verificar um IP passo a passo

  1. Obtenha o HELO. Envie um email a si próprio a partir da sua plataforma, abra-o no Gmail com «Mostrar original» e procure a linha Received: from mta1.exemplo.com (… [203.0.113.25]): o primeiro nome é o HELO e o que está entre parênteses retos é o IP real. Também pode enviar um email para helocheck@abuseat.org: o bounce indica-lhe o HELO que o seu servidor usa.
  2. Pergunte ao IP como se chama (PTR): nslookup 203.0.113.25. Tem de aparecer um nome.
  3. Pergunte ao nome que IP tem (registo A): nslookup mta1.exemplo.com. Tem de aparecer o mesmo IP.
  4. Compare com o HELO: tem de resolver para esse IP e, melhor ainda, ser igual ao PTR.

Sem terminal: na nossa ferramenta Informação de um IP cola a linha Received e ela verifica tudo. E se tiver muitos IPs, o seu modo Vários IPs verifica uma lista de pares IP e HELO e devolve OK, AVISO ou FALHA para cada um.

O NAT: a peça que quase ninguém vê

Pode ter o DNS perfeito e mesmo assim não cumprir. Muitas empresas têm os servidores de email dentro da sua rede com IPs privados (10.x, 172.16-31.x ou 192.168.x), e a firewall traduz-os para um IP público à saída: isso é o NAT. O recetor, e a Spamhaus, só veem o IP público, por isso o HELO e o PTR têm de coincidir com esse IP, não com o interno.

As falhas típicas:

  • Muitos para um: todos os servidores saem pelo mesmo IP público, cada um com um HELO diferente.
  • NAT desfasado: por um erro nas regras, cada servidor sai pelo IP do vizinho e o seu HELO aponta para outro IP.
  • Alterações não comunicadas: muda-se de firewall ou de fornecedor e ninguém revê os HELO.
  • Tráfego por omissão: os bounces ou os avisos do sistema saem por um IP público sem PTR próprio.

Para o verificar, veja o IP entre parênteses retos na linha Received de um email real enviado de cada servidor, ou peça a quem gere a rede a tabela de NAT de saída. A regra de ouro: um IP interno, um IP público, um nome, e que os três apontem uns para os outros.

Como corrigir sem estragar nada

  • Mude o mínimo: se um IP já cumpre, não lhe toque.
  • Se tiver de mudar um HELO, use o nome que já tem no seu PTR e aqueça-o aos poucos: a Spamhaus trata um HELO novo, sem histórico, como um ativo novo e aplica-lhe filtragem extra.
  • Os erros de configuração (gralhas, IPs trocados, HELO por omissão) corrige-os a sua equipa; o PTR é alterado por quem lhe dá o IP (fornecedor ou nuvem) e costuma demorar mais.
  • Faça limpeza de DNS: apague registos de máquinas que já não existem e evite curingas.
  • Se um IP já estiver na CSS, corrija primeiro a causa: a entrada expira sozinha cerca de três dias depois da última deteção. Veja o estado no Reputation Checker da Spamhaus.

Checklist

  • Tenho a lista completa de servidores que enviam email, incluindo os de testes, de reserva e de bounces.
  • Sei o IP público real de saída de cada um (verificado, não suposto).
  • Sei com que HELO se apresenta cada um.
  • Cada IP tem um PTR com um nome do meu domínio, não o genérico do fornecedor, e esse PTR volta ao IP.
  • Cada HELO resolve para o seu IP e, melhor ainda, coincide com o PTR.
  • Se enviar por IPv6, esses IPs cumprem o mesmo.
  • Revejo tudo isto a cada trimestre: as configurações degradam-se com o tempo.
