HELO, PTR and NAT: Spamhaus's new requirements

Since November 2026 Spamhaus checks how every mail server introduces itself. What it requires, how to check your IPs step by step and why NAT can break everything.

By María Luisa Duque · Email Deliverability Manager · Updated 2026-11-20

In this guide

  2. The pieces, in plain language

What has changed

On 21 October 2026 Spamhaus announced that, gradually from November, every IP that sends email must have a valid HELO, reverse DNS (PTR) and a matching A record. According to Spamhaus, failures on these points can get the IP listed on its CSS or XBL lists, which thousands of providers check before accepting an email.

It isn't a new idea: Gmail already requires valid forward and reverse DNS from all senders. What's new is that Spamhaus actively checks it, and a legitimate server can end up on the same list as an infected machine just for introducing itself badly.

The pieces, in plain language

Picture a courier arriving at a building's reception:

  • The IP is the van's number plate.
  • The PTR is what the plate registry says: who owns that van (the IP says what it's called).
  • The A record confirms that company really has that plate (the name says which IP it has).
  • The HELO (or EHLO) is what the courier says on arrival: «I'm from such-and-such company».

If all three match, the parcel goes through. If not, reception gets suspicious, and in email that means rejection or the spam folder. When the IP and its PTR confirm each other it's called FCrDNS (forward-confirmed reverse DNS).

What exactly Spamhaus requires

  • The IP has a PTR.
  • That name resolves to the same IP (FCrDNS).
  • The HELO is a full name (for example, mta1.mail.yourcompany.com) that resolves to the sending IP.
  • Recommended: the HELO matches the PTR.

And it explicitly forbids:

  • Placeholder values such as localhost or localhost.localdomain.
  • A HELO shaped like an IP.
  • The hosting provider's generic name (like ip-203-0-113-25.provider.net).
  • A HELO pointing to machines that don't send email or impersonating Gmail, Hotmail or other providers.

How to check an IP step by step

  1. Get the HELO. Send yourself an email from your platform, open it in Gmail with «Show original» and find the line Received: from mta1.example.com (… [203.0.113.25]): the first name is the HELO and the part in brackets is the real IP. You can also send an email to helocheck@abuseat.org: the bounce tells you the HELO your server uses.
  2. Ask the IP its name (PTR): nslookup 203.0.113.25. A name must come back.
  3. Ask the name its IP (A record): nslookup mta1.example.com. The same IP must come back.
  4. Compare with the HELO: it must resolve to that IP and, even better, be the same as the PTR.

Without a terminal: in our IP address information tool you paste the Received line and it checks everything. And if you have many IPs, its Several IPs mode checks a list of IP and HELO pairs and returns OK, WARNING or FAIL for each.

NAT: the piece hardly anyone checks

You can have perfect DNS and still fail. Many companies keep their mail servers inside their network with private IPs (10.x, 172.16-31.x or 192.168.x), and the firewall translates them to a public IP on the way out: that's NAT. The receiver, and Spamhaus, only see the public IP, so the HELO and the PTR must match that IP, not the internal one.

Typical failures:

  • Many to one: all servers leave through the same public IP, each with a different HELO.
  • Shifted NAT: because of a rule error, each server leaves through its neighbour's IP and its HELO points to another IP.
  • Unannounced changes: the firewall or provider changes and nobody reviews the HELOs.
  • Default traffic: bounces or system notices leave through a public IP with no PTR of its own.

To check it, look at the IP in brackets in the Received line of a real email sent from each server, or ask whoever runs the network for the outbound NAT table. The golden rule: one internal IP, one public IP, one name, all pointing to each other.

How to fix it without breaking anything

  • Change as little as possible: if an IP already complies, leave it alone.
  • If you must change a HELO, use the name it already has in its PTR and warm it up gradually: Spamhaus treats a new HELO with no history as a new asset and applies extra filtering.
  • Configuration errors (typos, crossed IPs, default HELO) are fixed by your team; the PTR is changed by whoever gives you the IP (your provider or cloud) and usually takes longer.
  • Clean up your DNS: delete records for machines that no longer exist and avoid wildcards.
  • If an IP is already on CSS, fix the cause first: the entry expires on its own about three days after the last detection. Check the status on Spamhaus's Reputation Checker.

Checklist

  • I have the full list of servers that send email, including test, backup and bounce servers.
  • I know the real public outbound IP of each one (checked, not assumed).
  • I know which HELO each one uses.
  • Every IP has a PTR with a name on my domain, not the provider's generic one, and that PTR points back to the IP.
  • Every HELO resolves to its IP and, even better, matches the PTR.
  • If I send over IPv6, those IPs meet the same requirements.
  • I review all this every quarter: configurations degrade over time.
