HELO, PTR et NAT : les nouvelles exigences de Spamhaus

Depuis novembre 2026, Spamhaus vérifie comment chaque serveur de messagerie se présente. Ce qu'il exige, comment vérifier vos IP pas à pas et pourquoi le NAT peut tout casser.

Ce qui a changé

Le 21 octobre 2026, Spamhaus a annoncé que, progressivement à partir de novembre, chaque IP qui envoie des emails doit avoir un HELO valide, un DNS inverse (PTR) et un enregistrement A correspondant. Selon Spamhaus, des erreurs sur ces points peuvent faire entrer l'IP dans ses listes CSS ou XBL, que des milliers de fournisseurs consultent avant d'accepter un email.

L'idée n'est pas nouvelle : Gmail exige déjà de tous les expéditeurs un DNS direct et inverse valide. La nouveauté, c'est que Spamhaus le surveille activement, et un serveur légitime peut se retrouver sur la même liste qu'une machine infectée simplement parce qu'il se présente mal.

Les pièces, sans jargon

Imaginez un coursier qui arrive à l'accueil d'un immeuble :

  • L'IP est la plaque d'immatriculation de la camionnette.
  • Le PTR est ce que dit le registre des immatriculations : à qui appartient cette camionnette (l'IP dit comment elle s'appelle).
  • L'enregistrement A confirme que cette entreprise a vraiment cette plaque (le nom dit quelle IP il a).
  • Le HELO (ou EHLO) est ce que dit le coursier en arrivant : « je viens de telle entreprise ».

Si les trois correspondent, le colis passe. Sinon, l'accueil se méfie, et dans l'email cela signifie un refus ou le dossier spam. Quand l'IP et son PTR se confirment mutuellement, on parle de FCrDNS (DNS inverse confirmé).

Ce qu'exige exactement Spamhaus

  • L'IP a un PTR.
  • Ce nom résout vers la même IP (FCrDNS).
  • Le HELO est un nom complet (par exemple mta1.envois.votreentreprise.com) qui résout vers l'IP d'envoi.
  • Recommandé : que le HELO corresponde au PTR.

Et il interdit expressément :

  • Les valeurs de remplissage comme localhost ou localhost.localdomain.
  • Un HELO en forme d'IP.
  • Le nom générique de l'hébergeur (du type ip-203-0-113-25.hebergeur.net).
  • Un HELO qui pointe vers des machines qui n'envoient pas de courrier ou qui se fait passer pour Gmail, Hotmail ou d'autres fournisseurs.

Comment vérifier une IP pas à pas

  1. Récupérez le HELO. Envoyez-vous un email depuis votre plateforme, ouvrez-le dans Gmail avec « Afficher l'original » et cherchez la ligne Received: from mta1.exemple.com (… [203.0.113.25]) : le premier nom est le HELO et ce qui est entre crochets, l'IP réelle. Vous pouvez aussi envoyer un email à helocheck@abuseat.org : le rebond vous indique le HELO de votre serveur.
  2. Demandez son nom à l'IP (PTR) : nslookup 203.0.113.25. Un nom doit apparaître.
  3. Demandez son IP au nom (enregistrement A) : nslookup mta1.exemple.com. La même IP doit apparaître.
  4. Comparez avec le HELO : il doit résoudre vers cette IP et, mieux encore, être identique au PTR.

Sans terminal : dans notre outil Informations sur une IP, collez la ligne Received et il vérifie tout. Et si vous avez beaucoup d'IP, son mode Plusieurs IP vérifie une liste de paires IP et HELO et renvoie OK, AVERTISSEMENT ou ÉCHEC pour chacune.

Le NAT : la pièce que presque personne ne regarde

Vous pouvez avoir un DNS parfait et ne pas être conforme pour autant. Beaucoup d'entreprises gardent leurs serveurs de messagerie dans leur réseau avec des IP privées (10.x, 172.16-31.x ou 192.168.x), et le pare-feu les traduit en une IP publique à la sortie : c'est le NAT. Le destinataire, et Spamhaus, ne voient que l'IP publique, donc le HELO et le PTR doivent correspondre à cette IP, pas à l'interne.

Les erreurs typiques :

  • Plusieurs vers une : tous les serveurs sortent par la même IP publique, chacun avec un HELO différent.
  • NAT décalé : à cause d'une erreur dans les règles, chaque serveur sort par l'IP de son voisin et son HELO pointe vers une autre IP.
  • Changements non signalés : on change de pare-feu ou de fournisseur et personne ne revérifie les HELO.
  • Trafic par défaut : les rebonds ou les avis système sortent par une IP publique sans PTR propre.

Pour le vérifier, regardez l'IP entre crochets dans la ligne Received d'un vrai email envoyé depuis chaque serveur, ou demandez à l'équipe réseau la table NAT sortante. La règle d'or : une IP interne, une IP publique, un nom, et que les trois se désignent mutuellement.

Comment corriger sans rien casser

  • Changez le minimum : si une IP est déjà conforme, n'y touchez pas.
  • Si vous devez changer un HELO, utilisez le nom qu'elle a déjà dans son PTR et chauffez-le progressivement : Spamhaus traite un HELO nouveau, sans historique, comme un actif nouveau et lui applique un filtrage supplémentaire.
  • Les erreurs de configuration (fautes de frappe, IP croisées, HELO par défaut) se corrigent en interne ; le PTR est modifié par celui qui vous fournit l'IP (fournisseur ou cloud) et cela prend souvent plus de temps.
  • Faites le ménage dans le DNS : supprimez les enregistrements de machines qui n'existent plus et évitez les jokers.
  • Si une IP est déjà dans CSS, corrigez d'abord la cause : l'entrée expire seule environ trois jours après la dernière détection. Vérifiez l'état dans le Reputation Checker de Spamhaus.

Checklist

  • J'ai la liste complète des serveurs qui envoient du courrier, y compris ceux de test, de secours et de rebonds.
  • Je connais l'IP publique réelle de sortie de chacun (vérifiée, pas supposée).
  • Je sais avec quel HELO chacun se présente.
  • Chaque IP a un PTR avec un nom de mon domaine, pas celui générique du fournisseur, et ce PTR renvoie vers l'IP.
  • Chaque HELO résout vers son IP et, mieux encore, correspond au PTR.
  • Si j'envoie en IPv6, ces IP respectent les mêmes exigences.
  • Je revérifie tout cela chaque trimestre : les configurations se dégradent avec le temps.
